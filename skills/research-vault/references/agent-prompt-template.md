# 並列調査エージェントの発注テンプレート

1トピック1エージェント。`<>` を埋めて general-purpose サブエージェントに渡す。
なぜこの形か: 文体見本の Read で品質を、実読 URL 限定で出典の信頼を、共有ファイル編集禁止で並列の衝突回避を、「書かなかった事項」の報告で検証の分離を、それぞれ担保する。

````text
「<トピック>」を Web 調査し、調査ノートを1ファイル作成してください。

## 出力先
<絶対パス>（新規作成。他のファイルは一切編集しないこと）

## 文体見本
まず <既存の良質ノートの絶対パス> を Read して、見出し構成・表・脚注の使い方を踏襲すること。

## 調査観点
- <観点1>
- <観点2>
- <誤記されやすい事実（登録制度・現職者・開始時期など）は「一次情報（<情報源>）で確認」と名指しする>

## ノート構成
H1 + 導入 → <主要な節> → 関連 → 脚注。
「## 関連」: <張るべき既存ノートへの WikiLink 行を列挙>

## 執筆ルール（厳守）
- 1行1文。箇条書き末尾に句点なし。固有名詞は初出時「カタカナ (原語)」
- Web 由来の記述には脚注 [^N]。実際に本文を読んで裏付けた URL のみ引用する
- 百科事典調の平叙文で書く
- 変動情報（料金・開館・現職者など）には「<YYYY-MM> 時点」を付す

## ツールの制約
- <このプロジェクトのフェッチ戦略。例: WebSearch 可／ページ本文は fetch-web スキルの手順に従う>

## 完了報告
作成したファイルパス、引用に使った URL 一覧、裏取りできず書かなかった事項、を簡潔に返すこと。
````

## 運用メモ

- 1波は5〜6件まで。波の完了ごとにレビューしてから次の波を出す
- 完了報告の「裏取りできず書かなかった事項」はレビューの主要な入力になる。空の報告は逆に疑う
- 既存ノートと主題が接するトピックでは、境界（どちらが正典か）をプロンプトに明記して重複を防ぐ
